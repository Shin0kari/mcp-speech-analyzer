# Правила работы над MCP Speech Analyzer

## Общение и требования
- Отвечать пользователю по-русски. Комментарии и проектную документацию писать по-русски; идентификаторы и имена протоколов — по-английски.
- Полное исходное задание хранится в `docs/product-spec.en.md`. Не сокращать требования молча.
- Работать поэтапно: проверка Codex → интерфейс и планировщик на имитации → двухканальный звук → русская транскрипция → модель → восстановление и MCP → длительные сессии.
- Отличать подтверждённые локальные проверки, документированные возможности и гипотезы. Сохранять результаты и ограничения проверок в `docs/` с датой и версией.
- Пользователь выбрал локальное распознавание речи. Отправка аудио в облако требует нового решения пользователя.
- Хранение аудио настраивается и по умолчанию выключено. Полный текст с временными метками и каналами сохраняется всегда. Временные аудиобуферы должны иметь ограниченный срок жизни.

## Codex и модель
- Сначала проверить установленный CLI, протокол и доступные модели по актуальной официальной документации и локальной схеме.
- Предпочтительная модель — `gpt-6.1-terra`; проверять через `model/list` и реальный тест. Не подменять её другой моделью или отдельно оплачиваемым API без решения пользователя.
- Подключение к существующему чату предпочтительно только при проверенных сохранении контекста, доставке сообщений, потоковых ответах и поведении UI.
- Не перезапускать общий сервер Codex и не вмешиваться в активные чаты ради диагностики. Для тестов использовать изолированную тестовую сессию.
- Сбой control socket в ограниченной среде не доказывает поломку интеграции или её причину. При ошибке разрешений/сети повторять необходимую проверку с надлежащим запросом разрешения.
- Резервный транспорт — отдельный `codex app-server` через stdin/stdout. Он не гарантирует общий контекст и синхронизацию с desktop UI.
- Фоновый анализ возвращает обычный структурированный результат, который приложение сохраняет без показа. Это не доступ к скрытым рассуждениям. Проверять, не становятся ли такие ходы видимыми в общем UI.
- Изолировать модель за адаптером. Передавать новый текст инкрементально; исходные цитаты должны оставаться доступными.
- Не добавлять независимый пятиминутный цикл сжатия контекста.

## Архитектура и захват
- Локальное приложение владеет UI, аудио, таймерами, хранилищем и оркестрацией. MCP предоставляет управление и чтение данных; само подключение MCP не запускает запись.
- Старт окна, старт сервера и старт записи — разные операции. Запись начинается только по явному действию пользователя или его явной команде.
- Два независимых канала: выбранный микрофон («Вы») и выбранный процесс с дочерними процессами («Собеседник»). Не заменять звук приложения общим системным loopback.
- Проверять совместимость Windows и реальное поведение дерева процессов браузера. Выбор браузера не означает изоляцию вкладки.
- Первый выбранный пользователем источник — Brave с воспроизводящей звук вкладкой. Короткий захват дерева Brave подтверждён; изоляция вкладки не подтверждена. См. `docs/brave-audio-check.ru.md`.
- В первой версии не делать диаризацию. Сохранять возможность её добавления.
- Отделять предварительные сегменты от окончательных; объединять каналы по времени. Обрабатывать исчезновение устройств и перезапуск источника.

## Состояние и конкурентность
- Хранить полный неизменённый текст, явный контекст пользователя, историю вопросов и их статусы; структурированное состояние не заменяет расшифровку.
- Одна последовательная очередь изменений состояния. Объединять повторные события в ограниченное число ожидающих операций.
- Ручной режим: фоновый анализ каждые 60 секунд, только при новом окончательном тексте.
- «Ответить» фиксирует границу аудио и сбрасывает таймер именно в момент клика. Дождаться окончательной транскрипции до границы, использовать успешный текущий анализ и обработать остаток. Более поздняя речь принадлежит следующему запросу.
- Граница обработки продвигается только вместе с успешно сохранённым результатом. Сбой/повтор не теряет сегменты; учитывать сбой между модельным ответом и сохранением.
- Автоматический режим: проверка примерно раз в 5 секунд, без перекрывающихся изменений состояния. Пустой результат допустим; подавлять повторы и устаревшие советы.
- По умолчанию отвечать только на актуальные вопросы, ещё не закрытые участниками или показанным ответом. Явный запрос пользователя может вернуть исторический вопрос. Не искать вопросы только по знаку «?».
- Не прокручивать чат принудительно, пока пользователь читает историю; предоставить возврат к новым сообщениям.

## Проверка
- Проверять таймеры управляемыми часами, границы и транзакции — воспроизводимыми тестами с имитатором модели/транскрипции.
- Обязательны: клик через 20 секунд после анализа; сброс таймера; pending-транскрипция; клик во время анализа; повторные клики; тишина; сбой модели и повтор; восстановление; исчезновение источника; метки каналов; естественно закрытый вопрос; отсутствие дублей; сохранение прокрутки; поиск исходного текста в долгой сессии.
- Не выдавать имитатор за готовый аудиозахват или реальное подключение модели. В UI и документации явно обозначать режим.
- Не коммитить записи разговоров, ключи, токены, локальные БД и приватные журналы. Диагностика должна выводить минимальные метаданные.
